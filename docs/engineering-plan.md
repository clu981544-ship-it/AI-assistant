# 工程实践与验收安排

2026-10-28 起，在足球助手功能路线中加入并发、可靠性与部署验收。目标是能解释问题、实施改进并提供测量证据；学习单元数量按实际验收调整。

## 当前代码基线

- `app/api.py` 固定用户和会话 ID 为 1，所有访问者共用历史与清空范围，尚无访问身份校验。
- 聊天路由与模型客户端采用同步调用；模型客户端未显式设置本应用的超时和重试策略，使用所安装 SDK 的默认行为。
- SQLite 每次操作单独连接、写入后提交；用户消息和模型回答分别保存，模型失败后可能只留下用户消息。
- 请求处理中的模型与数据库异常统一映射为 500，日志尚无贯穿完整请求的标识。
- 尚无并发压测结果，也没有已验证的吞吐量或容量承诺。

这些是后续练习的真实起点。当前优先完成规则数据与 RAG 的可验证链路，再沿请求链路逐项改进。

## 练习顺序与可观察结果

| 阶段 | 实际工作 | 验收证据 |
| --- | --- | --- |
| 数据准备和导入 | 明确来源版本、稳定片段 ID、重复导入策略；对需人工复核的图表保留边界 | 同一资料重复运行结果可比较；检索内容能回到原文；重复导入数量受控 |
| 会话与数据一致性 | 在开展多会话压测前移除固定会话，定义会话归属和访问校验；明确同一会话并行发送的顺序，以及清空与写入冲突的处理规则 | 两个独立会话互不读取或清空对方数据；并行请求与重复提交的数据状态符合约定 |
| 外部依赖与失败处理 | 显式定义模型和工具的超时、重试条件、总耗时预算、错误分类；给请求增加可追踪标识 | 用模拟依赖验证慢响应、服务不可用和恢复；失败状态可解释，重试不产生重复业务记录 |
| 建立性能基线 | 使用独立测试库、隔离会话与明确标注的模拟模型，运行 HTTP 压测，先测当前实现 | 保存命令、代码版本、硬件、测试时长、并发连接/在途请求数、吞吐量、P50/P95/P99 延迟、错误率及错误类型 |
| 定位并发瓶颈 | 观察应用线程、连接数、CPU/内存、数据库锁等待和依赖等待；依据结果选择异步 I/O、并发上限、排队或快速拒绝等改进 | 在相同条件下比较改动前后；超过容量时有明确反馈；过载解除后服务恢复，数据状态仍符合约定 |
| 数据库与部署 | 核对事务范围、索引、连接管理和 SQLite 写入限制；出现实际瓶颈后再决定 WAL 或 PostgreSQL；验证容器持久化、启动检查与退出行为 | 并发写入结果完整；重启后可读；部署文档可复现；扩容或更换存储的收益有测量依据 |
| 最终报告 | 使用完整业务请求和有限真实模型调用补测，记录模型限流、费用和延迟；列出容量边界与失败案例 | 区分模拟依赖与真实依赖的结果，给出已测负载下的表现及尚未验证的范围 |

## 并发练习怎么开展

先约定一个业务请求的正确结果，再测它在并发下是否仍然正确。例如，多个会话同时发送消息后，每个会话应只保存自己的完整记录；模型超时后，对应请求应进入明确状态，健康检查仍可响应。

压测从小负载开始逐步增加，例如 1、5、10、20 个同时在途请求；后续档位依据测量结果决定。每档运行足够时间、说明预热方式并记录成功与失败请求的耗时，避免只统计成功请求造成误判。并发数、每秒请求数和用户总量分别记录。

模拟模型的延迟与失败行为必须在报告中标明。此类结果用于隔离应用和数据库瓶颈；真实模型调用的结果另行报告，并明确上游配额和费用边界。

每次改进只调整有限因素，在同一环境和同一负载下比较。选择异步、增加 worker、缓存、数据库迁移等措施，都需要说明解决了哪一处已观察的问题，以及带来的新约束。

## 学习节奏

每个小闭环依次完成：定义预期行为、观察现状、实施修改、运行相应测试、记录结果和局限、提交代码。压测仅面向自己的隔离测试环境，使用标明用途的合成数据。

当前 Day 2 已完成来源核对、重复执行验证和元数据回归测试。Day 3 接着完成可追溯切分；上述工程任务在对应链路具备条件时实施，最终验收需要同时检查功能、正确性、失败处理和实测性能。
